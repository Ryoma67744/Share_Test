# 公開競合の無限再試行による接続障害の復旧

2026-11-06 に確認した症状は、`40001 / publish_conflict: reload and compare the shared copy` がほぼ毎秒記録され、通常の認証・読取APIまで `504 / PGRST003 / Timed out acquiring connection from connection pool.` になるものです。

アプリの版不一致に SQLSTATE `40001` を使うと、PostgREST 14 が同じトランザクションを繰り返す既知問題に該当します。業務上の競合は、再実行せず利用者による比較が必要なので、HTTP 409 に対応する `PT409` に変更します。

公式説明: <https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions-77326b>

## 既存サーバーの復旧

1. 作業中のアプリではローカル保存の完了を確認し、公開・同期操作を止めます。
2. 修正版アプリ（`v2026-11-06.1` 以降）を公開します。既存のタブは再読み込みしてください。新しいクライアントは `PT409` と従来の `40001` の両方を扱います。
3. 対象Supabaseプロジェクトの **SQL Editor → New query** を開き、[`conflict_error_hotfix.sql`](../supabase/conflict_error_hotfix.sql) 全体を貼り付けて **Run** を押します。既存DBのための専用SQLです。`schema.sql` や `share_locks.sql` 一式を再実行しないでください。
4. 結果の各 `ready` が `true` であることを確認します。エラーで終了した場合は変更をコミットしません。エラー本文を確認し、対象関数が想定と異なる場合はその定義を調べてから進めます。
5. すでに無限再試行中の処理は、関数の修正だけでは止まりません。対象プロジェクトの **Project Settings → General → Restart project** から再起動します。再起動中は一時的に接続できません。これはプロジェクトの削除や過去バックアップへの復元ではありません。
6. 管理画面の認証が応答することを確認します。公開競合があるプロジェクトは共有版と比較してから再公開します。競合を無視して上書きしません。

再起動の代わりに、管理者がPostgresログの `process_id` と `pg_stat_activity.pid` を照合し、ループ中の接続だけを終了する方法もあります。添付の統合ログの要約にはPIDが含まれないため、推測したPIDや全接続を対象にした終了SQLは用意しません。

## 変更範囲と確認

- 専用SQLは、既知の7関数にある12個の競合エラーコードだけを変更します。未導入の任意機能はスキップします。
- 対象のシグネチャ・競合コードの数が想定と違う場合は、トランザクション全体を中止します。再実行できます。
- プロジェクト・解析元データ・ROI・画像・MRM・認証情報の行は更新しません。関数の所有者・実行権限・認証判定・版照合は維持します。
- クライアントは競合後の自動公開を停止し、ローカル編集を保存しても自動再公開を再開しません。利用者が比較・再公開を明示したときに再開します。
- SQL移行は実際の関数定義を使うローカルPGliteテストで、権限・定義・データの保持、再実行、異常時の全体ロールバックを確認します。公開・共有編集・MRMの競合時データ保護は別のDB回帰テストでも確認します。

GitHubへのコード反映だけでは、既存Supabase内の関数は更新されません。専用SQLの適用と、既存のループ中接続を止める作業が必要です。

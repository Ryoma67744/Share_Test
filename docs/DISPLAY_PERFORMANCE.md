# 表示処理の再利用（2026-11-10）

表示設定の変更で同じ切片を二重に合成し、主画像とサムネイルが別々に原寸画像のRange適用・Medianを実行していた処理を整理しました。主画像の欠測背景は不透明、サムネイルは原画像のalphaを保持する既存の違いを維持しています。重ね合わせの単色配色と通常のサムネイル配色も別の出力として扱います。

原寸で求めた表示階調・Median結果を共有し、用途別に色とalphaを適用します。HEモノクロも同じ画像ならBT.601変換結果を再利用します。表示解像度、Rangeの式、MRM照合、原本、ROI統計、比の計算、Otsuの数値処理は変更していません。

## 描画とキャッシュ

- `setupCanvasSize`が描画まで完了した場合、呼び出し元は再描画しません。原画像が後から届いた場合の必要な再描画は維持します。
- ROIのみの表示でも、計算済みRangeによる設定変更後の追加描画を省きます。未完了のRangeは従来の完了通知で再描画します。
- UIの表示変更は`App.requestPanelDisplay`で要求し、画面外は更新待ちにします。Same Rangeの集計対象は画面外も含めて従来どおりです。
- `App.flushPanelDisplay`は同期で最新状態を確定します。PreviewはCanvasを読む前にこれを実行します。PPTとZIPは引き続き原本から出力します。
- MSIの表示階調・色付けCanvas、HEモノクロ、HE座標変換の派生キャッシュは全パネル共通64MiB上限です。大きすぎる結果は保持せず、その場の描画に使います。削除・原本差し替え・パネル破棄で対応する参照を解放します。
- Previewは更新予約を1フレームに集約します。同じセル構成ではDOMとpan/zoomを保持し、同じ描画世代・回転・寸法のPNGを再利用します。PNG文字列のキャッシュは最新1件/パネル、全体64MiB上限、終了・プロジェクト変更時に破棄します。
- キャッシュ上限は派生データの保持量です。原本、計算中の一時配列、ブラウザの画像デコーダ等を含むタブ全体のメモリ上限ではありません。

## ローカル測定

現行main `884dd4c`の監査時と同じ合成画像・ローカルheadless Chromiumの測定です。主画像とサムネイルの関数を続けて実行し、各試行の前にMSI表示キャッシュを破棄しています。PNG生成を含み、最終画面のpaint待ちは含みません。単一端末の少数試行で、実プロジェクトや本番の速度・改善率を保証する値ではありません。

| 条件 | 修正前 | 修正後 |
| --- | ---: | ---: |
| 補間方式1変更の同期合成回数/切片 | 2回 | 1回 |
| 400万画素・Smoothing Noneの主画像 | 183.0–199.2ms | 199.0–217.2ms |
| 同じ画像のサムネイル | 209.3–213.2ms | 38.2–41.4ms |
| 主画像＋サムネイルの合計 | 392.3–412.4ms | 240.4–255.4ms |
| 400万画素HEモノクロ・初回 | 78.5ms | 70.5ms |
| 同じHEモノクロ・2回目 | 208.2ms | 0.4ms |

初回の主画像自体が速くなったことを示す測定ではありません。重複したサムネイル処理と、反復するHE変換を減らしています。GC等によるばらつきがあるため、固定ミリ秒のCI判定には使いません。PreviewもPNGの符号化自体を高速化したのではなく、同じ結果の再符号化を避けます。
